# TODO: Full UI Integration Plan

This document is the integration checklist for importing the full UI and wiring every workflow end-to-end across the React frontend, FastAPI backend, SQLite-backed screening state, JSON-backed list/search state, and LLM/search services.

## 1. Integration Goal

- Make the imported UI behave as one continuous pipeline: screening intake, criteria analysis, keyword search, list creation, LLM screening, final list compilation, and output export.
- Preserve existing backend conventions: thin routers, app-state services, atomic JSON-backed state, and shared search/index behavior.
- Keep all user-visible workflow state resumable from persisted backend state, not only browser memory.

## 2. Current Architecture to Preserve

- Backend application assembly lives in [`main.py`](backend/app/main.py) through [`create_app()`](backend/app/main.py:91); keep service creation centralized there.
- Frontend API helpers live in [`endpoints.ts`](frontend/src/api/endpoints.ts); add every new frontend backend call there.
- Frontend shared HTTP behavior lives in [`client.ts`](frontend/src/api/client.ts); keep global toast/error behavior centralized there.
- Active screen and local pipeline UX state live in [`screenStore.ts`](frontend/src/stores/screenStore.ts).
- Screening state persists in SQLite through [`screenings_repo.py`](backend/app/storage/screenings_repo.py) and business logic in [`screenings.py`](backend/app/services/screenings.py).
- JSON-backed list/search/history state is managed through repository/service layers; any new JSON write should use existing repository functions and atomic save behavior rather than ad-hoc writes.

## 3. End-to-End Workflow to Integrate

### 3.1 Screening Intake

- UI entry: [`ScreeningIntakePage.tsx`](frontend/src/pages/ScreeningIntakePage.tsx).
- Backend router: [`screenings.py`](backend/app/routers/screenings.py).
- Backend service: [`screenings.py`](backend/app/services/screenings.py).
- Required integration behavior:
  - Upload PDF and persist canonical file by PDF hash.
  - Deduplicate by PDF hash and show the duplicate selection dialog.
  - Store normalized snake-case screening fields only.
  - PATCH edits into existing `edited_fields` instead of replacing the full object.
  - Start screening only after Screen Name is present.
  - Starting a screen must mark it active in backend state and sync frontend active-screen state.

### 3.2 Active Screen Global State

- UI indicator: [`ActiveScreenBar.tsx`](frontend/src/components/layout/ActiveScreenBar.tsx).
- Store: [`screenStore.ts`](frontend/src/stores/screenStore.ts).
- Backend source of truth: active screening row from [`screenings_repo.py`](backend/app/storage/screenings_repo.py).
- Required integration behavior:
  - On app boot, fetch active screening from backend and hydrate [`screenStore.ts`](frontend/src/stores/screenStore.ts).
  - When the green active-screen bar appears, all screen-aware pages default their screen filter/selectors to that active screen.
  - User-selected filters may override the default until the active screen changes.
  - Dropdown trigger labels must show Screen Name, falling back to original filename only if Screen Name is missing; never show raw id as the selected label unless no display metadata exists.

### 3.3 Criteria Analysis

- Frontend page: [`CriteriaAnalysisPage.tsx`](frontend/src/pages/CriteriaAnalysisPage.tsx).
- Backend router: [`criteria_analysis.py`](backend/app/routers/criteria_analysis.py).
- Existing frontend API helpers: [`analyzeCriteria()`](frontend/src/api/endpoints.ts), [`markCriteriaProgress()`](frontend/src/api/endpoints.ts), [`refineCriteria()`](frontend/src/api/endpoints.ts), [`rerunCriteriaAnalysis()`](frontend/src/api/endpoints.ts).
- Required integration behavior:
  - Replace stub LLM outputs with real imported UI/LLM pipeline output while keeping the same response shape.
  - Persist criteria-analysis stage after the user reaches Questions, Final Criteria, and Keyword Search stages.
  - Reopening criteria analysis must resume the persisted stage instead of replaying accordions step-by-step.
  - If final criteria already exists, open directly at Final Criteria state.
  - The Repeat button must confirm before clearing current final criteria and resetting criteria-analysis progress in the database.
  - Final criteria generated by the real LLM must be saved to `curr_final_criteria` on the screening row.
  - Criteria questions and answers should eventually be persisted if the imported UI requires resume inside step 2, not only stage-level resume.

### 3.4 Keyword Generation and Search

- Search page: [`SearchPage.tsx`](frontend/src/pages/SearchPage.tsx).
- Search hooks/store: [`useSearch.ts`](frontend/src/hooks/useSearch.ts), [`searchStore.ts`](frontend/src/stores/searchStore.ts).
- Backend router/service: [`search.py`](backend/app/routers/search.py), [`search.py`](backend/app/services/search.py).
- Shared engine: [`company_screener/`](company_screener/).
- Required integration behavior:
  - Criteria Analysis must pass generated keyword rows and query expression into search state.
  - Search should support auto-apply from route state without requiring the user to manually click Search again.
  - Large result-set operations must remain server-side; use existing cached-search paging and list insertion patterns.
  - Ensure search results include enough primary key/company metadata for downstream list and LLM screening operations.

### 3.5 Lists

- Lists page: [`ListsPage.tsx`](frontend/src/pages/ListsPage.tsx).
- Add-to-list dialog: [`AddToListDialog.tsx`](frontend/src/components/search/AddToListDialog.tsx).
- Backend router/service: [`lists.py`](backend/app/routers/lists.py), [`lists.py`](backend/app/services/lists.py).
- Required integration behavior:
  - Every list can optionally carry `screening_id` and Screen Name.
  - Creating a list while a screen is active should default association to the active screen where appropriate.
  - The list sidebar filter defaults to the active screen when an active screen exists.
  - Dropdown selected labels show Screen Name, not ids.
  - Running LLM Screening from a list must pass list name, screening id, and generated prompts through route state.
  - Lists without associated screen should still be runnable by letting the user fill prompts manually in LLM Screening.

### 3.6 LLM Screening

- Page: [`LLMScreeningPage.tsx`](frontend/src/pages/LLMScreeningPage.tsx).
- Platform flow: [`PlatformScreenFlow.tsx`](frontend/src/components/llmScreening/PlatformScreenFlow.tsx).
- Independent flow: [`IndependentUseCaseFlow.tsx`](frontend/src/components/llmScreening/IndependentUseCaseFlow.tsx).
- Backend router: [`llm_screening.py`](backend/app/routers/llm_screening.py).
- Required integration behavior:
  - Imported UI should receive prompts from backend if a list has a screen association.
  - If no screen association exists, prompt cards should start blank and require user review/fill.
  - Start run should send selected list companies, prompts, model, batch size, rationale settings, and screening id to backend.
  - Backend should create a durable LLM screening run/job record if runs can be paused/resumed or audited.
  - Results table must use real company identifiers from list entries, not stub ids.
  - Add to Final List must add the selected companies, regardless of Yes/Maybe/No decision, because the user may curate manually.
  - Final-list creation should preserve `screening_id`, Screen Name, decision, rationale, and source metadata.
  - ERROR reruns should target only selected or visible error rows, depending on imported UI behavior.

### 3.7 Final List and Output Compilation

- Output page: [`OutputCompilationPage.tsx`](frontend/src/pages/OutputCompilationPage.tsx).
- Export dialog: [`ExportDialog.tsx`](frontend/src/components/search/ExportDialog.tsx).
- Backend exports: [`exports.py`](backend/app/routers/exports.py), [`exports.py`](backend/app/services/exports.py).
- Required integration behavior:
  - Final list should be discoverable by active screen and Screen Name.
  - Output compilation should default to final list for the active screen.
  - Export should include selected final-list companies plus decision/rationale metadata from LLM Screening.
  - Completing output should update active screen pipeline state to completed.

## 6. State Passing Between Pages

### 6.1 Screening Detail to Criteria Analysis

- Route to `/criteria-analysis/:screeningId`.
- Pass optional route state with seeded screening payload only for just-created drafts.
- Backend remains source of truth once screening exists.

### 6.2 Criteria Analysis to Search

- Use route state from [`CriteriaAnalysisPage.tsx`](frontend/src/pages/CriteriaAnalysisPage.tsx) to [`SearchPage.tsx`](frontend/src/pages/SearchPage.tsx):
  - `autoApplyKeywords`
  - `generatedKeywords`
  - `generatedQueryExpression`
  - active `screening_id` if downstream list association requires it.

### 6.3 Search to Lists

- Use [`AddToListDialog.tsx`](frontend/src/components/search/AddToListDialog.tsx) to create or append to lists.
- Include active `screening_id` and Screen Name by default when active screen exists.
- For very large result sets, use server-side cached insertion rather than sending all rows through the browser.

### 6.4 Lists to LLM Screening

- Navigate to `/llm-screening` with route state:
  - `flow`
  - `listName`
  - `screeningId`
  - `prompts`
  - `needsPromptFill`
- If `screeningId` exists, backend generated prompts should be loaded before review.
- If `screeningId` is missing, prompt cards should be blank and user editable.

### 6.5 LLM Screening to Final List

- Send selected result rows to backend with:
  - list name for final list
  - source list name
  - screening id
  - selected company primary keys
  - decision/rationale metadata
  - run id
- Do not infer final list membership only from Yes decisions; use explicit selected rows.

## 7. Persistence Requirements

- Persist active screen in backend and hydrate frontend from backend on load.
- Persist pipeline step/status after every major workflow step.
- Persist `curr_final_criteria` when final criteria is generated.
- Persist LLM screening run inputs and outputs when real LLM execution is integrated.
- Persist final-list membership with enough metadata to regenerate exports.
- Keep frontend store as UX cache only; backend state must win after refresh.

## 8. Error Handling Requirements

- Frontend API functions should use shared error-toasting in [`client.ts`](frontend/src/api/client.ts), except when page-level custom retry UI is required.
- Long-running backend calls should disable timeout explicitly in [`endpoints.ts`](frontend/src/api/endpoints.ts).
- LLM prompt generation failures should show retry UI and keep the source list selected.
- Criteria-analysis reset should require confirmation and show a success/failure toast.
- LLM screening run failures should preserve partial results and expose rerun options.

## 11. Suggested Integration Order

1. Hydrate active screen from backend on app boot and verify screen-aware defaults.
2. Integrate real criteria-analysis backend output while preserving current UI resume behavior.
3. Persist criteria questions/answers if needed by imported UI.
4. Integrate keyword generation into Search with auto-apply.
5. Integrate list association defaults and large server-side list insertion.
6. Add durable LLM screening run endpoints.
7. Replace LLM screening stub results with real run progress/results.
8. Implement selected-row final-list insertion with decision/rationale metadata.
9. Wire output compilation to active-screen final list.
10. Add backend and frontend regression tests for each pipeline transition.

## 12. Final Acceptance Criteria

- A user can upload or resume a screen, activate it, and see the green active-screen bar.
- Lists and LLM Screening default to the active screen and show Screen Name in dropdown triggers.
- Criteria Analysis resumes wherever it was left and only restarts after explicit Repeat confirmation.
- Final criteria is persisted in the database and reused for LLM prompt generation.
- Search results can be added to lists without browser-scale row transfer for large sets.
- LLM Screening can run on list companies and produce durable results.
- Add to Final List inserts exactly the rows the user selected.
- Output export can be produced from the final list for the active screen.
- Refreshing the browser does not lose backend-backed workflow progress.
